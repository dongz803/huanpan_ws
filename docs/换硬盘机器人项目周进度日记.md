# 第一周（2026年9月1日—2026年9月7日）

## 本周目标

建立换硬盘机器人项目的基础工作区，先完成不依赖ROS控制的UR5e MuJoCo基础仿真，再逐步接入ROS 2、MoveIt 2、夹具和硬盘机柜。

## 本周进度

1. 建立工作区 `/home/lzt/huanpan_ws`，明确项目目标为服务器硬盘自动抓取、搬运和插入。
2. 建立UR5e纯MuJoCo基础模型，完成模型加载、关节数量、执行器数量和有限状态检查。
3. 初步接入ROS 2 Humble和MoveIt 2，建立机械臂状态、规划和轨迹执行链路。
4. 根据实物尺寸建立硬盘架基础模型：
   - 机柜正面宽度：430 mm；
   - 机柜高度：85 mm；
   - 机柜深度：175 mm；
   - 排列方式：横向4个、纵向3个，共12个盘位；
   - 单块硬盘尺寸：175 mm × 100 mm × 25 mm。
5. 在仿真初期将同尺寸硬盘长方体固定到机械臂末端，作为末端link，用于先验证插入运动，不在这一阶段处理抓取过程。

## 遇到的问题

1. 一开始对机柜“3列4行”和“4列3行”的方向理解不一致，导致模型排列方向错误。
2. 全量构建MoveIt 2源码时占用大量内存和CPU，电脑出现严重卡顿，存在构建中途假死的问题。
3. MuJoCo模型、ROS URDF和MoveIt模型来源不同，容易出现外观、关节名称和坐标轴不一致。

## 尝试的方法

1. 根据实际照片和尺寸反复核对机柜方向，而不是继续沿用最初的文字描述。
2. 尝试直接在工作区内编译MoveIt 2源码，确认项目可以使用源码版本，但发现没有必要每次都全量重编。
3. 先用最小纯MuJoCo场景检查UR5e模型，再逐步叠加ROS 2、MoveIt 2和工作站模型。

## 解决方法与结论

1. 最终统一为“横向4个、纵向3个”的12盘位结构。
2. MoveIt 2源码保留在工作区，但日常修改只构建项目相关包；需要构建大型依赖时采用单线程或低并行度，例如 `--parallel-workers 1`。
3. 确定“先验证纯MuJoCo模型，再接ROS控制”的顺序，避免模型错误和控制错误混在一起排查。

## 下周计划

完善夹具、硬盘、机柜和机械臂的统一模型，补齐MoveIt 2配置及分层代码框架。

# 第二周（2026年9月8日—2026年9月14日）

## 本周目标

完善UR5e末端工具和工作站模型，建立清晰的ROS 2、MoveIt 2及MuJoCo代码架构，并跑通基本规划与可视化。

## 本周进度

1. 参考已有AG95 URDF和mesh资源建立夹具模型，并将其连接到UR5e末端。
2. 完善硬盘架和硬盘模型，保留硬盘作为末端固定link的测试方案。
3. 建立MoveIt 2配置包和启动文件，补充SRDF、OMPL、控制器、运动学和RViz配置。
4. 将应用层按职责划分为：

   ```text
   kinematics
   control
   collision_checking
   motion_planning
   trajectory_processing
   ```

5. 建立MuJoCo与ROS 2之间的关节状态和轨迹执行接口，使MoveIt 2规划结果能够发送给仿真。
6. 增加分层README，说明各模块入口、输入输出和启动顺序。

## 遇到的问题

1. 早期框架主要参考实机驱动工程，只有实机接口，没有明确的MuJoCo仿真接口。
2. RViz中的机械臂和夹具外观与MuJoCo不一致，夹爪连接位置和模型方向存在偏差。
3. RViz可以生成运动请求，但MoveIt规划或执行失败；MuJoCo中同时显示大量link/坐标轴，影响观察。
4. 仿真中没有显示末端携带的硬盘，无法直观看到插入过程。

## 尝试的方法

1. 参考旧实机工程的URDF、夹具mesh和相机连接方式，但不直接覆盖当前ROS 2仿真配置。
2. 对比MuJoCo、URDF和RViz中的TF链、关节原点和mesh尺度。
3. 用与硬盘同尺寸的简单长方体替代真实硬盘mesh，先解决几何和运动问题。
4. 分别检查MoveIt规划失败、控制器连接失败和碰撞检测失败，避免只根据RViz提示判断原因。

## 解决方法与结论

1. 在代码框架中同时保留实机驱动接口和MuJoCo仿真接口，运动规划层不直接绑定某一种执行端。
2. 统一UR5e、夹具和末端硬盘的TF连接关系，RViz和MuJoCo使用相同的关节命名和基本几何约定。
3. 当前阶段使用硬盘长方体作为末端固定link，暂时不处理夹爪开合和抓取接触。
4. 明确MoveIt 2负责规划，MuJoCo桥负责执行和状态反馈，两者之间使用ROS 2控制接口连接。

## 下周计划

建立自动插入测试，加入扰动、接触力检测和超力后退逻辑；同时开始规划视觉感知路线。

# 第三周（2026年9月15日—2026年9月21日）

## 本周目标

完成仿真插入安全链路，并从零建立D435真实图像采集、YOLO粗定位和精定位技术路线。

## 本周进度

### 仿真与运动部分

1. 为12个盘位补充 `slot_00_entry`～`slot_11_entry` 及对应目标坐标系。
2. 建立 `insertion_demo` 自动测试，支持到达预插入点后执行直线插入。
3. 加入Ornstein-Uhlenbeck有色关节扰动，用于测试机械臂在扰动下的轨迹稳定性。
4. 加入力保护模块：接触力滤波、持续超阈值判断、锁存、停止轨迹和沿历史轨迹撤退。
5. 仿真执行模块完成19项单元测试，其中包括扰动可复现性、力阈值和撤退目标选择。

### 视觉部分

1. 决定暂时不使用仿真相机数据，直接使用真实D435采集，因为真实机柜存在反光、黑色网格和复杂背景。
2. 新建 `huanpan_perception` ROS 2包，打通采集、标注、训练、评估、离线推理和ROS节点运行链路。
3. 完成少量真实图像采集和YOLOv8n粗定位训练，验证从图像到检测框的最小闭环。
4. 确定精定位总体路线：

   ```text
   YOLO粗框
   → 框附近四边拟合
   → 四边求交得到四角
   → 已知尺寸100×25 mm
   → IPPE/PnP输出相机坐标系下6D位姿
   → 深度平面检查
   → 与示教位姿比较
   ```

5. 明确当前手持相机只是替代未来的腕部相机进行视觉算法验证，现阶段不能把相机坐标直接当作机械臂基坐标。

## 遇到的问题

1. 自动插入测试出现：

   ```text
   MoveGroupInterface::execute() failed or timeout reached
   Nominal insertion failed; max force 30.67 N
   ```

2. 扰动虽然使用固定随机种子，但每次MoveIt规划耗时不同，导致插入开始时落在不同扰动相位，名义插入也可能触发力保护。
3. ROS 2 Humble的 `cv_bridge` 与虚拟环境NumPy 2存在ABI不兼容。
4. Torch安装在Python虚拟环境中，而 `ros2 run` 默认使用系统Python，节点启动方式不统一。
5. 视频连续帧过于相似，随机切分训练集和验证集会产生数据泄漏，使mAP虚高。

## 尝试的方法

1. 调低扰动和力阈值，发现只能暂时掩盖问题，不能保证测试可复现。
2. 分析插入前后的扰动序列，确认问题来自扰动开始时间而不是MoveIt连接失败。
3. 尝试直接使用 `cv_bridge`，根据报错进一步定位到NumPy ABI问题。
4. 尝试直接从长视频逐帧训练，发现近重复图像数量多但视角变化很少。

## 解决方法与结论

1. 增加 `/mujoco/disturbance/reset` 服务：机械臂到达entry后重置扰动序列，再开启力保护并开始插入。修复后一次名义插入测试最大力约3.02 N并通过。
2. 自行实现 `sensor_msgs/Image` 与NumPy数组转换，绕开 `cv_bridge` 的ABI问题。
3. 入口程序加入虚拟环境重执行机制，使 `ros2 run`、launch和直接运行使用相同Python环境。
4. 视频抽帧加入时间间隔和近似去重，训练/验证集按视频片段分组切分。
5. 粗定位阶段只负责提供ROI，不把YOLO轴对齐框中心直接当作毫米级插入坐标。

## 下周计划

完善D435的RGB、对齐深度和CameraInfo同步采集；实现并测试四边拟合、IPPE/PnP及示教位姿比较。

# 第四周（2026年9月22日—2026年9月28日）

## 本周目标

完成手持条件下的精定位原型，解决RGB-D同步、GPU推理、调试图帧率和精定位稳定性问题。

## 本周进度

1. 将彩色图、对齐到彩色坐标系的深度图和CameraInfo组成同步输入，保存RGB、16位深度、内参和帧元数据。
2. 确认RGB、深度和CameraInfo必须属于同一分辨率和同一相机内参，不能混用640×480和1280×720数据。
3. 建立经典精定位算法：
   - 在YOLO框四周使用Sobel梯度寻找上下左右边；
   - 每一侧保留多个边缘候选；
   - 使用Huber鲁棒直线拟合；
   - 四条直线求交得到四角；
   - 使用100×25 mm平面矩形运行IPPE/PnP；
   - 通过重投影误差、边缘质量和边界距离选择结果。
4. 增加PnP结果、深度平面、示教参考姿态和相对修正量输出。
5. 配置RTX 3060和CUDA版PyTorch。实测YOLO单次推理约4.3 ms，总模型处理约6.23 ms，说明模型计算本身不是低帧率主因。
6. 修复调试图发布链路：
   - 调试图QoS改为 `BEST_EFFORT`、队列深度1；
   - 没有订阅者时跳过画框和序列化；
   - 调试预览缩放到最大宽度640；
   - 避免整帧RGB/BGR重复转换。
7. 将深度采样区域从槽口内部改为绿色精定位框外侧的一圈机柜面板，避免空槽内部、后壁和黑色区域产生错误深度。

## 遇到的问题

1. `/huanpan/vision/debug_image` 最初只有约4.7 Hz，而相机输入约30 Hz。
2. 状态记录显示YOLO只需约10 ms，但 `debug_publish` 曾达到约190 ms，证明主要瓶颈是大尺寸ROS图像消息的绘制、序列化和发布。
3. 使用GPU后YOLO速度明显提高，但整体帧率没有同步提高，说明优化方向不能只盯模型推理。
4. 精定位只在特定距离和近似正视时稳定；相机倾斜、过近或过远时绿色四边形闪烁或识别失败。
5. 出现“PnP深度与D435深度相差过大”和“重投影误差超过2 px”等警告。
6. 槽口内部为空且相邻硬盘面板突出，不同区域并不属于同一个深度平面。

## 尝试的方法

1. 将YOLO从CPU切到GPU，确认模型推理速度很快，但没有单独解决ROS端到端帧率。
2. 调整输入尺寸和可视化尺寸，比较相机话题、检测话题、状态话题和调试图话题频率。
3. 尝试放宽重投影误差和深度差阈值，但发现只放宽阈值会让错误四边形也通过。
4. 尝试在槽口内部读取深度，发现空洞、后壁和反光导致深度不稳定。
5. 加入多帧位姿滤波、连续确认和跳变拒绝，减轻单帧闪烁。

## 解决方法与结论

1. 低帧率的主要原因不是ROS 2共享内存报错，也不是YOLO算力不足，而是调试图发布和后续几何处理叠加。
2. 通过降低调试图通信开销，调试图频率提升到约16 Hz以上；粗检测图曾达到约20～30 Hz。
3. 深度只在槽口外侧面板区域做RANSAC平面拟合，槽口内部不再参与深度定位。
4. PnP深度与面板深度的差异改为诊断项，当前 `enforce_pnp_depth_consistency: false`，避免相邻突出硬盘造成误拒绝。
5. 确认精定位前需要先把相机姿态调整到近似正视，否则四边拟合和IPPE会对透视、反光和错误边缘非常敏感。

## 下周计划

将“姿态调整”和“严格精定位”拆成两个阶段；继续补充倾斜视角数据，并重新验证精定位稳定性。

# 第五周（2026年9月29日—2026年10月5日，截至9月30日）

## 本周目标

先建立稳定的相机正视反馈，再进入X/Y位置和完整6D精定位；同时继续补充单槽口数据和优化实时性。

## 本周进度

1. 继续采集并标注单个槽口图像，统一标签标准，重新训练 `slot_opening` 单类别YOLO模型。
2. 排查Fast DDS共享内存端口报错。相机原始话题仍约30 Hz，说明该提示不是检测低帧率的根因。
3. 将粗定位框固定显示为黄色，将严格精定位四边形固定显示为绿色，避免不同阶段结果混淆。
4. 增加独立“正视阶段”，当前设置：

   ```yaml
   front_view_only: true
   require_front_view_alignment: true
   ```

   因而当前只进行姿态反馈，不执行绿色精定位和X/Y位置调整。
5. 当前正视方法最终确定为：

   ```text
   YOLO黄色粗框
   → 黄色框外侧深度点反投影
   → RANSAC拟合局部平面，法向计算pitch/yaw
   → 黄色框内部灰度化、Canny、HoughLinesP
   → 边主方向计算roll
   → 连续5帧满足阈值后输出FRONT_ALIGNED
   ```

6. 发布相机坐标系下的相对旋转反馈：
   - `/huanpan/vision/front_view_correction`：旋转向量，单位rad；
   - `/huanpan/vision/front_view_aligned`：是否连续稳定正视；
   - `/huanpan/vision/status`：角度、法向、质量和耗时诊断。
7. 使用已有 `capture_00035.png` 对框内长边算法做离线可视化测试：YOLO置信度约0.883，估计roll约-7.70°，长边质量约0.887。
8. 保留原严格精定位代码，准备在正视稳定后重新启用：Sobel四边候选、Huber直线拟合、四边求交、IPPE/PnP、重投影检查、深度检查和多帧滤波。

## 遇到的问题

1. 相机倾斜时，YOLO仍只能输出轴对齐黄色矩形，不能直接反映目标四边形的透视形状。
2. 初次尝试在黄色框内部寻找“粗四边形”，再用较宽松门限运行IPPE估计正视姿态。结果出现：
   - 容易把槽内纹理或近似水平矩形当成目标边界；
   - 即使重投影误差很低，也不代表选中的四边形是正确物理槽口；
   - 四边形接近轴对齐时可能错误判断为已经正视；
   - 相比原来的深度法向方法，实际效果更差。
3. 粗四边形候选枚举和多次IPPE增加了明显计算量。一次状态记录中 `front_view` 约110 ms，回调总耗时约195 ms。
4. 大尺寸调试图发布仍会占用通信和序列化时间。因此当粗IPPE计算和图像发布叠加时，实时链路压力进一步增大。
5. 需要注意：通信压力主要来自调试图消息；粗IPPE主要增加计算压力，二者不能混为同一个原因。

## 尝试的方法

1. 尝试“粗四边形 + 宽松IPPE”作为姿态调整依据，允许较大的重投影误差，希望在严格精定位前获得初始姿态。
2. 使用框外深度平面只做交叉检查，试图避免突出硬盘面板影响姿态判断。
3. 对比粗IPPE法向和深度平面法向，发现二者曾相差约24.9°，说明粗四边形选错后会给出误导性姿态。
4. 将当前阶段设置为 `front_view_only`，强制停止在姿态调整阶段，防止黄色粗框和绿色精定位框同时显示。
4. **同时根据考虑了视觉最终需求和以及目的是“将硬盘停在尽可能精准的槽口前位置进行插入”，于是加入了位姿反馈这个步骤，还有一点就是考虑到了当时的问题是当视角是斜的时候就检测不到槽口，于是现在粗定位阶段阶段这个问题，也就是给yolo更多的数据集。**

## 解决方法与结论

1. 删除正视阶段的“粗四边形 + 宽松IPPE”方法，恢复之前更直接的方案：
   - 框外深度平面法向负责pitch/yaw；
   - 框内Hough长边负责roll；
   - IPPE只保留给后续严格精定位，不再用于当前粗姿态调整。+
   
2. 当前阶段只显示黄色YOLO框和姿态反馈，不显示绿色精定位框。

3. 正视反馈只包含旋转，不包含X/Y平移；后续机械臂接入时，需要通过手眼标定和TF把相机坐标系旋转向量转换到 `base_link`。

   

## 下一步计划

1. 使用已有图片批量可视化和评估外侧深度平面、Hough长边及输出姿态。
2. 正视阶段稳定后，将 `front_view_only` 改为 `false`，重新启用绿色严格精定位。
3. 对严格精定位重点检查：
   - 四条边是否对应真实槽口边界；
   - 四角是否稳定；
   - 重投影误差是否真实反映几何正确性；
   - 不同距离和轻微偏角下是否连续输出；
   - XYZ和旋转是否满足3 mm/1°的阶段目标。
4. 手持视觉验证完成后，再固定D435到UR5e末端，完成手眼标定和相机坐标系到机器人基坐标系的转换。
